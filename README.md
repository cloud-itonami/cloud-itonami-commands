# cloud-itonami-commands

The command surface of `cloud-itonami-app`, as a dependency: what an
operator can name, what each name resolves to, and what a repository is
allowed to say about its own bot. Two pure namespaces and three tables.

```
src/cloud/itonami/app/commands.cljk       every command, longest-prefix match,
                                          path templating, flags, aliases
src/cloud/itonami/app/repo_profile.cljk   <repo>/.itonami/profile.edn, admitted or refused by name
resources/cloud-itonami-app.commands.edn      GENERATED by the app from its routes
resources/cloud-itonami-app.cli-aliases.edn   the reviewed alias table
resources/cloud-itonami-app.defaults.edn      the app's configuration defaults
```

## Why a repository

Three front ends read these: the terminal `itonami`
([cloud-itonami-cli](https://github.com/cloud-itonami/cloud-itonami-cli)),
the mobile bundle (`cloud-itonami-app/mobile`), and the app's own JVM `cli`.
Until 2026-09-15 each carried a copy. The CLI pinned the three tables and ran
a checker to notice drift; the mobile build reached into `../src ../resources`
with a path tools.deps deprecates. Measured that day, three of the CLI's four
pinned files had drifted from the app that generates them (commands 409→414
routes, aliases +18 lines, defaults rewritten). A copy with a checker is still
a copy.

So the contract is one repository every consumer pins by git sha, and the
question "is the CLI's table current?" becomes the ordinary one, "is the pin
current?", answered by the same pin discipline as every other dependency.
Nothing here depends on the app, the CLI, or the mobile bundle.

The namespaces keep the names they always had (`cloud.itonami.app.commands`,
`cloud.itonami.app.repo-profile`) so that no consumer's `require` changes.

## Who writes the registry

`cloud-itonami-app` does. `dev/gen_commands.cljk` in the app scans
`server.cljk`'s routes and writes `resources/cloud-itonami-app.commands.edn`
**into this repository's checkout** (`../cloud-itonami-commands` beside the
app, or `--out <path>`). The app's `commands-test` re-derives the registry
and fails when the copy on its classpath — this repository at the pinned
sha — no longer matches its routes. Adding a route is therefore:

1. land the route in the app;
2. regenerate here, land here;
3. advance the sha in the app's `deps.edn`, the CLI's `nbb.edn` + `deps.edn`,
   and `mobile/deps.edn`.

Step 3 is the step that used to be silent.

## Tests

```bash
kbb -M:test      # 32 tests / 128 assertions on the kbb engine
```

`commands_tables_test` reads the shipped tables the way the terminal front
end does (`install-sources!`, no classpath) and asks what a front end asks;
`repo_profile_test` pins every refusal's `:reason` literal.

## Consumers

| consumer | how it depends | what it reads |
|---|---|---|
| cloud-itonami-cli `bin/itonami` | `nbb.edn` `:deps` git sha | both namespaces, all three tables (from the engine's classpath) |
| cloud-itonami-app | `deps.edn` git sha | `commands` (cli.cljk, route_scan, commands-test), `defaults.edn` (config), `cli-aliases.edn` (tests) |
| cloud-itonami-app/mobile | `mobile/deps.edn` git sha | `commands` + the two tables it inlines |
